# ТЗ-02 — Заказы: жизненный цикл и финансовый snapshot

**Исполнитель:** субагент «доменная модель заказов».  
**Исходное ТЗ:** §9, §10, §16.  
**Зависимости:** ТЗ-01 (копейки).  
**Блокирует:** ТЗ-03 (частично), ТЗ-06, ТЗ-07, ТЗ-12, админка заказов.

## Цель

Появление сущности **заказ** с неизменяемым финансовым снимком и статусами:

`CREATED → PROCESSING → COMPLETED | FAILED | EXPIRED | REFUNDED`.

Пользователь **не** отменяет оплаченный заказ. Вывода средств нет.

## Контекст кода

Сейчас покупка сразу создаёт `BoughtGoods` и списывает баланс. Нет статусов, нет закупочной цены, комиссии, прибыли, внешнего ID поставщика, истории статусов.

`BoughtGoods` — выданный контент (ключ). Его сохранить и связать с заказом.

Неоплаченный заказ в текущей модели почти не существует: оплата идёт через баланс (сначала top-up). «Неоплаченный» появится, если заказ резервирует товар до списания — согласовать с ТЗ-03/06: либо `CREATED` до списания короткий TTL, либо заказ создаётся уже после проверки баланса (`CREATED` мгновенно в `PROCESSING`). Оба варианта допустимы, **TTL EXPIRED обязателен** для `CREATED` без оплаты/списания.

## Задача

1. Модели: `Order`, `OrderStatusHistory` (кто/когда/из какого статуса).
2. Поля заказа (все деньги — копейки): пользователь, товар, qty, price, discount, total, cost (закупка), fee, referral_amount, profit, delivery_type (`STOCK`/`API`/`GIFT`), provider_id nullable, provider_external_order_id nullable unique, fulfillment_payload (выдача), `gift_telegram_id` nullable, timestamps created/completed.
3. Snapshot: копировать цены и закупку **в момент создания/оплаты**, дальше `Goods.price` не влияет.
4. Сервис статусов: только разрешённые переходы; каждый переход пишет history.
5. Ручной refund оператором: `COMPLETED|FAILED → REFUNDED`, возврат `total` на баланс **идемпотентно** (повторный refund ноль).
6. Пользовательский cancel оплаченного — запрещён (нет кнопки, API отвергает).
7. Миграция Alembic; связь `BoughtGoods.order_id`.

## Направление

- Enum статусов строками как в ТЗ (совместимо с SQLAdmin).
- `profit = total - cost - fee - referral_amount` считать при переходе в COMPLETED и сохранить; не пересчитывать из актуальных цен.
- Не класть HTTP поставщика в эту задачу.

## Вне скоупа

Реализация Wizard, Platega, UI подарка (поле `allows_gift` может быть заглушкой).

## Критерии приёмки

- [ ] Таблицы `orders`, `order_status_history` в миграциях.
- [ ] Невозможны нелегальные переходы (тест матрицы).
- [ ] Изменение `Goods.price` после COMPLETED не меняет `order.total` / `profit`.
- [ ] Повторный ручной refund не начисляет баланс дважды.
- [ ] Оплаченный заказ нельзя отменить пользовательским методом.
- [ ] `CREATED` старше TTL → `EXPIRED` (логика может жить в ТЗ-12; здесь — поле `expires_at` и чистая функция перехода).
- [ ] Уникальность `provider_external_order_id` где задан (защита retry поставщика — используют ТЗ-05/06).

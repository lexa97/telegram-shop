# ТЗ-03 — Каталог и складской товар

**Исполнитель:** субагент «склад / каталог».  
**Исходное ТЗ:** §3.1, §6, админка склада.  
**Зависимости:** ТЗ-01, желательно ТЗ-02 (связь единицы с заказом).  
**Блокирует:** ТЗ-06 STOCK-ветка, массовая загрузка в ТЗ-10.

## Цель

Складской товар: единица содержит код/ключ/логин/URL/текст. При покупке **одна** доступная единица блокируется и не может уйти двум покупателям. Тип товара `STOCK` vs `API`. Опционально «можно дарить».

## Контекст кода

- `Goods` + `ItemValues` (`value`, `is_infinity`).
- Покупка: `buy_item_transaction` — `FOR UPDATE` на user, goods, item value.
- Infinity: одна и та же строка выдаётся многократно (не удаляется).
- Уникальность `(item_id, value)` — одинаковый ключ дважды на товар нельзя.
- Restock notify: `StockSubscriptions`.

Нет: `fulfillment_type`, gift, статусов единицы (available/reserved/sold), резерва до оплаты.

## Задача

1. Поля `Goods`: `fulfillment_type` (`STOCK`|`API`), `allows_gift` bool, опционально `unlimited` вместо только infinity-строки — не ломать infinity.
2. Жизненный цикл складской единицы: `AVAILABLE → RESERVED → SOLD` (или удаление как сейчас + явный reserved). Для API-товаров склад пустой.
3. Резерв в той же транзакции, что списание (если заказ сразу PROCESSING) **или** резерв на TTL при CREATED — согласовать с ТЗ-02/06, описать в MEMORY.
4. Конкурентная покупка: `SELECT … FOR UPDATE SKIP LOCKED` (предпочтительно) или retry как сейчас.
5. Массовая загрузка значений: сервис приёма списка строк (файл/текст), дедуп, отчёт об ошибках. UI админки может быть в ТЗ-10, **сервис — здесь**.
6. Товары API не требуют `ItemValues` для продажи (проверка в ТЗ-06).

## Направление

- Не тащить HTTP в каталог.
- Infinity-товары трактовать как STOCK с неограниченной выдачей одного шаблона (VPN-конфиг общий и т.п.).
- Подарок: единица выдаётся **получателю** (telegram_id), оплачивает покупатель; контент не слать покупателю если это секрет (направление: покупателю — «подарок отправлен», получателю — ключ). Точная копия текстов — ТЗ-11.

## Вне скоупа

Provider, Platega, тикеты.

## Критерии приёмки

- [ ] Два параллельных покупателя одного последнего ключа: ровно один SUCCESS, второй «нет в наличии»; ключ в БД не дублируется у двух `BoughtGoods`/`Order`.
- [ ] Зарезервированная единица недоступна третьему покупателю.
- [ ] Снятие резерва при EXPIRED/FAILED возвращает единицу в AVAILABLE (тест).
- [ ] Массовый импорт 100 ключей создаёт 100 AVAILABLE; дубликат строки — ошибка/скип с отчётом, не падает весь импорт.
- [ ] `API`-товар нельзя «выдать со склада» этим модулем.
- [ ] `allows_gift=false` — сервис покупки в подарок отвергает (даже если UI ещё нет).

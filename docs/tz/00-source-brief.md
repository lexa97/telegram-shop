# Краткое техническое задание
## Telegram-магазин цифровых товаров

### 1. Общая информация

Необходимо адаптировать существующий open-source проект `interlumpen/Telegram-shop` под специализированный Telegram-магазин цифровых товаров.

Готовая платформа используется как техническая основа проекта. Она уже предоставляет базовые механизмы каталога, пользователей, внутреннего баланса, склада, промокодов, реферальной системы, ролей, административной панели, статистики и обработки платежей.

Основная задача разработки заключается не в создании магазина с нуля, а в адаптации существующей платформы под требуемую бизнес-логику, подключении Platega и внешних поставщиков цифровых товаров, а также в расширении системы автоматической выдачи товаров.

Репозиторий основы: `interlumpen/Telegram-shop`.

### 2. Основные возможности

Пользователь взаимодействует с магазином через Telegram-бота.

Основной функционал:

- регистрация пользователя через Telegram;
- каталог цифровых товаров;
- категории и карточки товаров;
- внутренний баланс;
- пополнение баланса через Platega;
- покупка товаров за внутренний баланс;
- автоматическая выдача цифровых товаров;
- покупка товара для себя или в подарок, если это поддерживается конкретным товаром;
- промокоды;
- реферальная система;
- история заказов;
- поддержка пользователей;
- административная web-панель;
- статистика и отчёты.

Первая версия работает только с российским рублём.

### 3. Типы товаров

Система должна поддерживать два основных механизма получения товара.

#### 3.1. Складской товар

Товар заранее закупается и хранится в собственном складе магазина.

Каждая единица товара может содержать отдельное значение:

- код;
- ключ;
- логин/пароль;
- URL;
- иной текстовый цифровой контент.

При покупке одна доступная единица резервируется и после успешной оплаты передаётся пользователю.

Примеры:

- Gift Card;
- код активации;
- VPN-ключ;
- лицензионный ключ;
- иной заранее закупленный цифровой товар.

#### 3.2. API-товар

Товар приобретается непосредственно у внешнего поставщика через API в момент оформления заказа.

Система не должна быть жёстко связана с конкретным поставщиком.

Для этого вводится абстракция поставщика (`Provider`).

Архитектура:

```text
Product
   ├── STOCK
   │     └── Stock Items
   │
   └── API
         └── Provider Product
                └── Provider
```

Один и тот же товар потенциально может иметь несколько поставщиков.

Например:

```text
Telegram Premium
    ├── Provider A
    └── Provider B

Steam Gift Card
    ├── Provider A
    └── собственный склад
```

Это позволяет менять поставщика без изменения пользовательского интерфейса и основной логики магазина.

### 4. Интеграция поставщиков

Должен быть реализован единый интерфейс внешнего поставщика.

Минимальный набор операций:

```python
class Provider:
    async def get_product(...):
        ...

    async def create_order(...):
        ...

    async def get_order_status(...):
        ...

    async def cancel_order(...):
        ...
```

Конкретные реализации подключаются отдельными адаптерами.

Например:

```text
Provider
├── WizardProvider
├── DatamollProvider
└── OtherProvider
```

Конкретная реализация API не должна попадать непосредственно в модель товара или обработчики Telegram-бота.

Для API-товара необходимо хранить:

- поставщика;
- внешний ID товара;
- параметры покупки;
- закупочную стоимость;
- правила формирования запроса;
- правила обработки результата;
- настройки timeout/retry;
- параметры выдачи результата пользователю.

Это позволит в дальнейшем добавлять новых поставщиков без переработки всей системы.

### 5. Покупка API-товара

Общий сценарий:

```text
Пользователь
    ↓
Выбор товара
    ↓
Создание заказа
    ↓
Проверка баланса
    ↓
Списание средств
    ↓
Создание заказа у Provider
    ↓
Получение результата
    ↓
Выдача пользователю
    ↓
COMPLETED
```

При временной ошибке поставщика используется повторная попытка согласно настройкам.

Если покупка у поставщика окончательно не удалась, средства пользователя возвращаются на внутренний баланс.

Повторная обработка одного заказа не должна приводить к повторной покупке товара у поставщика.

### 6. Покупка складского товара

Сценарий:

```text
Пользователь
    ↓
Выбор товара
    ↓
Создание заказа
    ↓
Блокировка доступной единицы склада
    ↓
Списание средств
    ↓
Выдача товара
    ↓
SOLD
    ↓
COMPLETED
```

При одновременной покупке одного товара несколькими пользователями одна единица склада не может быть выдана более одного раза.

Используются PostgreSQL-транзакции и блокировки строк.

### 7. Внутренний баланс

Пользователь имеет внутренний баланс.

Баланс используется для оплаты товаров.

Пополнение осуществляется через Platega. При этом нужно учесть, что могут подключаться другие системы приёма платежей. 

Лучше всего приём платежей разбить на две части - выбор платежного инструмента и привязка внешней платежной системы для этого инструмента.

Например - карты мир процессим через Platega, крипту через Heleket и так далее.

Настройку платежных системы надо вынести в конфиг в бд и управлять этим через административный интерфейс

Все операции с балансом должны выполняться атомарно.

Необходимо исключить:

- двойное зачисление;
- двойное списание;
- отрицательный баланс вследствие гонки запросов;
- повторное начисление средств при повторной обработке webhook.

Для финансовых значений используется integer в копейках.

Например:

```text
299 ₽ → 29900
999 ₽ → 99900
```

В БД не используются `float`, `double` и аналогичные типы для денежных значений.

Предпочтительный тип: `BIGINT`.

### 8. Платежи

Подключается платёжная система Platega.

Необходимо реализовать:

- создание платежа;
- получение платёжной ссылки;
- обработку webhook;
- проверку статуса платежа;
- зачисление средств на баланс;
- защиту от повторного webhook;
- сохранение информации о платеже.

Каждый внешний платёж должен иметь уникальный идентификатор.

Повторная доставка webhook не должна повторно зачислять деньги.

### 9. Заказы

Заказ должен иметь жизненный цикл.

Основные статусы:

```text
CREATED
PROCESSING
COMPLETED
FAILED
EXPIRED
REFUNDED
```

Для каждого заказа сохраняются:

- пользователь;
- товар;
- количество;
- цена;
- скидка;
- итоговая стоимость;
- закупочная стоимость;
- комиссия;
- реферальное вознаграждение;
- прибыль;
- тип доставки;
- поставщик;
- внешний ID заказа поставщика;
- результат выдачи;
- дата создания;
- дата завершения;
- история изменения статусов.

Финансовые параметры заказа сохраняются в виде snapshot на момент покупки.

Изменение цены товара после покупки не должно изменять исторические данные заказа.

### 10. Отмена и возвраты

Оплаченный заказ пользователь самостоятельно отменить не может.

Неоплаченный заказ имеет ограниченный срок жизни и после его истечения переводится в `EXPIRED`.

Если API-поставщик не смог выполнить заказ:

```text
FAILED
    ↓
Refund
    ↓
Баланс пользователя
```

Возврат производится на внутренний баланс.

Оператор также может выполнить ручной возврат средств на внутренний баланс.

Вывод средств из внутреннего баланса в первой версии не реализуется.

### 11. Промокоды

Поддерживаются:

- процентная скидка;
- фиксированная скидка;
- бонус на внутренний баланс.

Необходимо учитывать:

- срок действия;
- количество использований;
- лимит на пользователя;
- минимальную сумму заказа;
- доступность для определённых товаров/категорий при необходимости.

Одно использование промокода должно фиксироваться атомарно.

### 12. Реферальная система

Пользователь может получить персональную реферальную ссылку.

При выполнении условий покупки рефереру начисляется вознаграждение.

Начисление должно выполняться только один раз для конкретного заказа.

Реферальное вознаграждение фиксируется отдельно от основного баланса и заказа.

### 13. Административная панель

Административная web-панель должна предоставлять управление:

- пользователями;
- балансами;
- товарами;
- категориями;
- складом;
- API-поставщиками;
- связями товаров с поставщиками;
- заказами;
- платежами;
- промокодами;
- рефералами;
- обращениями пользователей;
- статистикой;
- ролями;
- аудитом.

Для API-товаров администратор должен иметь возможность указать:

- поставщика;
- внешний ID товара;
- закупочную цену;
- параметры API;
- розничную цену;
- настройки автоматической выдачи.

Для складских товаров должна быть возможность массовой загрузки значений склада.

### 14. Роли

Предусмотреть разграничение доступа.

Основные роли:

```text
SUPERADMIN
ADMIN
OPERATOR
MANAGER
```

Права должны определяться ролью пользователя.

Критические действия администратора должны записываться в audit log.

### 15. Поддержка пользователей

Пользователь должен иметь возможность создать обращение в поддержку через Telegram-бота.

Администратор/оператор может:

- просматривать обращения;
- отвечать пользователю;
- изменять статус обращения;
- просматривать связанные заказы.

История переписки сохраняется.

### 16. Финансовая модель

Для каждого завершённого заказа необходимо иметь возможность определить:

```text
Цена продажи
- Скидка
= Итоговая цена

Итоговая цена
- Закупочная стоимость
- Комиссии
- Реферальное вознаграждение
= Прибыль
```

Все значения сохраняются в копейках.

Финансовая информация исторического заказа не должна зависеть от последующих изменений товара, поставщика или цен.

### 17. Надёжность и идемпотентность

Система должна быть защищена от повторной обработки операций.

В частности:

- повторный webhook не зачисляет деньги дважды;
- повторное списание не уменьшает баланс дважды;
- один складской код не продаётся двум пользователям;
- один заказ поставщика не создаётся повторно при retry;
- одно реферальное вознаграждение не начисляется несколько раз;
- повторный запрос на выдачу не приводит к повторной выдаче товара.

Для критических операций используются PostgreSQL transactions, unique constraints и row-level locking.

### 18. Фоновые задачи

Фоновый worker используется для:

- обработки заказов в `PROCESSING`;
- повторных попыток API-запросов;
- проверки зависших заказов;
- истечения неоплаченных заказов;
- проверки статусов внешних заказов;
- других длительных операций.

Telegram-бот не должен блокироваться на длительных операциях внешнего API.

### 19. Техническая основа

Используется существующий проект `interlumpen/Telegram-shop`.

Основной стек:

- Python 3.11+;
- aiogram 3;
- FastAPI;
- PostgreSQL;
- SQLAlchemy 2;
- asyncpg;
- Alembic;
- Redis при необходимости;
- SQLAdmin;
- Docker.

Существующий функционал проекта используется максимально повторно.

Не требуется переписывать с нуля уже реализованные механизмы, если они соответствуют требованиям проекта.

При необходимости существующие модели и бизнес-логику необходимо адаптировать.

Особое внимание уделяется существующим денежным полям: они должны быть приведены к хранению денежных значений в целых копейках (`BIGINT`).

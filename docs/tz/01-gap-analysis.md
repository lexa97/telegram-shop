# Разрыв между ТЗ и текущим кодом

Документ для агентов: что уже есть и чего нет. Не реализовывать отсюда — только ориентир.

## Чего нет (обязательно по ТЗ)

1. Хранение денег в копейках (`BIGINT`).
2. Сущность заказа со статусами CREATED…REFUNDED и snapshot финансов.
3. Типы товара STOCK / API и абстракция `Provider`.
4. Любой адаптер внешнего цифрового поставщика (Wizard и т.д.).
5. Platega: create payment, link, webhook, status.
6. Разделение «платёжный инструмент» vs «шлюз» и конфиг в БД / админке.
7. Покупка «себе / в подарок».
8. Тикеты поддержки (сейчас кнопка — URL на helper).
9. Ручной возврат заказа оператором на баланс; авто-refund при FAIL API.
10. Реферал с заказа + уникальность на заказ.
11. Роли SUPERADMIN/ADMIN/OPERATOR/MANAGER как в ТЗ (можно смапить на биты).
12. Worker для retry API, expire неоплаченных, hung PROCESSING.

## Осознанные решения для агентов (не отвергать без записи в MEMORY)

- **Не удалять корзину** — это сильнее ТЗ и уже в проде платформы.
- **Не делать Mini App**.
- **Не делать вывод** с внутреннего баланса.
- **Рефералка:** перенести триггер с top-up на `Order.COMPLETED`; процент по-прежнему из настроек, snapshot в заказ.
- **BoughtGoods** оставить как запись выданного контента (ключ), связать `order_id`.
- **Роли:** сохранить битовую модель `Permission`; добавить/переименовать роли под ТЗ, не ломая `HasPermissionFilter`.
- **Валюта v1:** RUB; CryptoPay/Stars можно оставить как шлюзы, но инструменты и включение — из БД.

## Риски

- Массовая миграция `Numeric` → копейки затронет тесты, i18n (`int(amount)`), split корзины (`_split_amount`).
- Смена реферала сломает ожидание пользователей «бонус с пополнения» — это требование ТЗ, зафиксировать в админских текстах.
- API поставщика без песочницы: ТЗ-05 обязан дать fake/sandbox адаптер для тестов.
